# Deterministic sanitizing beats classifiers for marq

No maintained, fully local, stdio-transparent product with confirmed tool-output injection scanning exists as of 2026-11-17, and the best offline classifier (Llama Prompt Guard 2) catches only a minority of indirect injections in tool output. The recommendation for marq is therefore to build the cheap deterministic layer in-house at `runner.Run`: strip invisible and control characters, cap and label free text, wrap it in a nonce-delimited untrusted block, and mark remote-controlled fields in structured output. Document a classifier as an opt-in sidecar rather than bundling one, because Prompt Guard 2 is Llama-licensed and gated, no Go-native runtime handles its tokenizer cleanly, and independent measurements put its indirect-injection recall at roughly 7-70% depending on the benchmark. Of the MCP proxies, Trail of Bits' mcp-context-protector is the only purpose-built stdio wrapper that scans responses, and it was archived on 2026-11-06. Docker's MCP Gateway offers an `after` interceptor hook that is the most practical integration point for a user-supplied scanner. Spotlighting-style delimiting gives small measured gains on modern models and fails against adaptive attackers, so it is worth having for provenance but should not be sold as a control. Architectural limits (Rule of Two, CaMeL-style flow control) are the only approaches with near-zero measured attack success, and they live in the client; marq's job is to make them attainable by keeping read and egress tools separate and labelling provenance.

## Offline classifiers catch too little indirect injection to be a gate

Meta's Prompt Guard 2 remains the reference small classifier: the 86M variant is mDeBERTa-base and the 22M variant is DeBERTa-xsmall, both with a **512-token context** and a benign/malicious output only ([HF card](https://huggingface.co/meta-llama/Llama-Prompt-Guard-2-86M)). Meta reports AUC .998 English / .995 multilingual for the 86M model and 97.5% recall at 1% FPR, with A100 latency of **92.4 ms (86M) and 19.3 ms (22M)** per 512 tokens; on AgentDojo it reports 81.2% attack-prevention at a 3% utility cost for 86M versus 22.2% for ProtectAI's model ([HF card](https://huggingface.co/meta-llama/Llama-Prompt-Guard-2-86M)). These are vendor numbers on Meta's own sets, and independent work is much less flattering. A 2026 study replaying 15 detectors on AgentDojo and tau-bench tool outputs found that detector performance does not transfer between benchmarks (one catching 72% on AgentDojo caught 15% on tau-bench), that false-positive rates on benign tool output ranged from none to over 90%, and recommends evaluating on the agent's own outputs ([arXiv 2610.03448](https://arxiv.org/abs/2610.03448)). Another paper reports detection as low as **7-37% on indirect and tool-use injections** for Prompt Guard 2 86M and Llama Guard 3 8B combined ([arXiv 2602.14161](https://arxiv.org/abs/2602.14161)). In the one Go-relevant replication of an agent pipeline, a DeBERTa detector cut AgentDojo attack success to roughly 1-3% but roughly halved utility (61.5 to 34.1 on gpt-oss-120b) ([arXiv 2601.04795](https://arxiv.org/html/2601.04795v1)). The classifier also scores text in isolation and only the first 512 tokens, so an injection buried deep in a long OTX pulse can slip past, and Meta advises chunking and scanning segments ([HF card](https://huggingface.co/meta-llama/Llama-Prompt-Guard-2-86M)).

Evasion is a second problem. Hackett et al. bypassed the Prompt Guard v1-era model 100% of the time with emoji smuggling, Unicode tags, zero-width and bidirectional characters, and bypassed ProtectAI v2 100% with emoji smuggling and tags ([arXiv 2504.11168](https://arxiv.org/html/2504.11168v3)). Prompt Guard 2 was not covered, so its robustness is unmeasured, but the finding argues for normalizing text before any classifier sees it, which is precisely the deterministic layer recommended below. Meta's own card warns of adaptive-attack vulnerability. Alternatives are weak: ProtectAI deberta-v3-base-prompt-injection-v2 is Apache-2.0 but English-only and archived ([HF](https://huggingface.co/protectai/deberta-v3-base-prompt-injection-v2)), and 2026 community models such as Galvanize 3 (Apache-2.0, about 140M, multilingual, 512 tokens) report results on private sets only ([HF](https://huggingface.co/usezn/Galvanize-3)). An open benchmark run by the vendor of one entrant shows wide spread in real-chat false positives (Prompt Guard 2 22M 0.77%, 86M 4.88%, ProtectAI v2 8.82%) ([pi-detector-bench](https://github.com/bastion-soft/pi-detector-bench)); that is chat traffic, not WHOIS or DNS TXT, and no source measured benign instruction-like text such as SPF strings or README-style bios, which is the case marq cares about most. Multilingual coverage is limited to Prompt Guard 2 86M (evaluated on EN, FR, DE, HI, IT, PT, ES, TH); Russian, Chinese, Arabic and Korean OSINT sits outside Meta's evaluated set.

### Licensing and Go runtime friction

Prompt Guard 2 ships under the Llama 4 Community License and is gated on Hugging Face. Redistribution is allowed but requires including the agreement, prominently displaying "Built with Llama" on related documentation, a Notice file with Meta's copyright line, and AUP compliance; a fine-tuned derivative must also carry a name beginning with "Llama" ([Llama 4 LICENSE](https://github.com/meta-llama/llama-models/blob/main/models/llama4/LICENSE)). The 700M-MAU clause is irrelevant to marq. Bundling it would therefore make every marq image a pass-through of that license plus a build-time HF token. Whether a Docker image counts as a "product" needing in-product display is unconfirmed (this is a practical read, not legal advice), and the safe design is optional download at first run rather than bundling. Apache-2.0 models avoid all of this.

The runtime story is the harder blocker. onnxruntime_go needs cgo and a matching ORT shared library you must supply for linux/amd64 ([GitHub](https://github.com/yalue/onnxruntime_go)); hugot offers a pure-Go backend plus an ORT backend and a text-classification pipeline ([GitHub](https://github.com/knights-analytics/hugot)). The tokenizer is the real gap: DeBERTa-v2/mDeBERTa uses SentencePiece Unigram, and the notes found no established pure-Go Unigram implementation (eliben's go-sentencepiece is BPE only) ([Bendersky](https://eli.thegreenplace.net/2024/sentencepiece-bpe-tokenizer-in-go/)); daulet/tokenizers works but pulls a Rust library through cgo ([go-huggingface](https://github.com/gomlx/go-huggingface)). llama.cpp supports BERT classification heads but no DeBERTa classifier was found. Naive int8 quantization is also hazardous: one ONNX export of Prompt Guard 2 86M dropped from recall 0.9625 to 0.8018 when quantized ([gravitee card](https://huggingface.co/gravitee-io/Llama-Prompt-Guard-2-86M-onnx)). Size is a further cost against a 1.9 GB image: the 86M model's mDeBERTa embedding matrix puts the fp32 file near 1 GB (inferred, not confirmed), while int8 community builds of other detectors run 81-233 MB. CPU latency for Prompt Guard 2 was not published anywhere found; I would guess tens of ms (22M) to a few hundred ms (86M) per window but that must be measured. An in-process Go classifier therefore means two cgo libraries, an unverified tokenizer path and a license pass-through, in exchange for a gate that misses most indirect injections.

## No proxy delivers local, transparent output scanning today

Trail of Bits' mcp-context-protector is the closest match to the requirement. It wraps a stdio server (`--command-args docker run --rm -i marq`), pins server configuration trust-on-first-use, sanitizes ANSI codes, and with `--guardrail-provider LlamaFirewall` quarantines flagged responses for human release ([README](https://github.com/trailofbits/mcp-context-protector#readme)). It is Apache-2.0, Python, local-only, and **archived since 2026-11-06 with no tagged releases** ([repo](https://github.com/trailofbits/mcp-context-protector)); its scanning is only as good as LlamaFirewall's Prompt Guard 2 (torch, transformers; last PyPI release 1.0.3 in May 2025) ([PurpleLlama](https://github.com/meta-llama/PurpleLlama/tree/main/LlamaFirewall)). Pinning would also trigger re-approval whenever marq's tool catalog changes. It is usable as a pinned fork or reference design, not a dependency.

Docker's MCP Gateway (MIT, Go, v0.44.3, active) is the best hook point: `--interceptor=after:exec:...` hands the tool response as JSON on stdin and accepts a replacement on stdout, though the project calls the interceptor example experimental, and its built-in `--block-secrets` covers secrets, not injection ([interceptors README](https://github.com/docker/mcp-gateway/blob/main/examples/interceptors/README.md), [security docs](https://github.com/docker/mcp-gateway/blob/main/docs/security.md)). Whether it can front an arbitrary local image without a catalog entry was not verified, and it has had critical advisories in 2026 ([advisories](https://github.com/docker/mcp-gateway/security)). ToolHive (Apache-2.0, Go, very active) gives container isolation, Cedar authorization and audit but no injection scanner ([repo](https://github.com/stacklok/toolhive)). IBM ContextForge has a `tool_post_invoke` plugin hook and can wrap stdio via `translate`, but ships no confirmed injection classifier and carries a heavy stack with a poor 2026 advisory record ([plugins](https://github.com/IBM/mcp-context-forge/blob/main/plugins/README.md)). The SaaS-leaning options fail the privacy constraint: Snyk Agent Scan (formerly Invariant's mcp-scan) needs a SNYK_TOKEN, uploads tool metadata, and is a scanner rather than a proxy ([README](https://github.com/snyk/agent-scan#readme)); Lasso's injection detection requires its API key ([repo](https://github.com/lasso-security/mcp-gateway)); Invariant Gateway defaults to pushing traces to its hosted Explorer and has been quiet since late 2025 ([repo](https://github.com/invariantlabs-ai/invariant-gateway)); Cloudflare's offering is hosted. LLM Guard is archived and NeMo Guardrails is a dialogue framework without MCP output integration ([LLM Guard](https://github.com/protectai/llm-guard), [NeMo](https://github.com/NVIDIA-NeMo/Guardrails)). None of these has production-user evidence in the notes, and all Prompt Guard-based filters inherit the classifier limits above.

## Deterministic techniques are cheap, but only some are measured

Spotlighting was introduced by Microsoft with delimiting, datamarking and encoding variants and cut attack success from over 50% to under 2% on GPT-family models ([Hines et al.](https://arxiv.org/html/2403.14720v1)). The authors themselves do not recommend plain delimiting because an attacker who knows the delimiters can imitate them. Independent evaluation on modern open models is far less generous: on AgentDojo, delimiting-style spotlighting moved average ASR only from 7.93 to 6.51 (gpt-oss-120b), 10.49 to 6.72 (llama-3.1-70b) and 10.33 to 8.41 (qwen3-32b), versus 1.7-2.6% for a non-LLM tool filter and 0.1-0.3% for LLM-based tool-result parsing at a 10-15 point utility cost ([arXiv 2601.04795](https://arxiv.org/html/2601.04795v1)). Another 2026 evaluation saw spotlighting raise ASR on GPT-4o-mini from 10.0% to 13.3% (secondary snippet) ([arXiv 2605.11026](https://arxiv.org/pdf/2605.11026)), and a study of 12 defenses including spotlighting reports adaptive attackers exceeding 90% ASR against most ([Nasr, Carlini et al.](https://arxiv.org/html/2510.09023v1)). I found no study of per-call random nonce delimiters, so their benefit is an inference: the attacker cannot forge a closing tag they cannot predict, which removes the one weakness the Spotlighting authors flagged, but it does not stop the model from obeying text inside the block. Datamarking is a poor fit for marq because it mangles hashes, IPs and paths the model must reuse; encoding hurts weaker models. Microsoft's own production stance is defense in depth, with probabilistic layers that can block legitimate actions ([MSRC](https://www.microsoft.com/msrc/blog/2025/07/how-microsoft-defends-against-indirect-prompt-injection-attacks)), and the UK NCSC warns against deny-lists of known attack phrases ([NCSC](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection)).

Character-level sanitizing is unmeasured on benchmarks but closes demonstrated covert channels. Unicode tag characters U+E0000-E007F render invisibly yet are read by models, and Embrace The Red reports Anthropic models interpreting them as instructions ([Embrace The Red](https://embracethered.com/blog/posts/2025/amazon-q-developer-interprets-hidden-instructions)); "Sneaky Bits" shows stripping tags alone is insufficient because two invisible characters can encode arbitrary bytes ([post](https://embracethered.com/blog/posts/2025/sneaky-bits-and-ascii-smuggler)); Microsoft saw tag smuggling in a high-volume phishing campaign in September 2026 ([Microsoft](https://www.microsoft.com/en-us/security/blog/2026/09/03/ascii-smuggling/)). Trail of Bits showed ANSI escape sequences hiding instructions (white-on-white, line overwrite, spoofed OSC 8 links) in MCP output that Claude Code did not filter at the time, and suggests replacing any 0x1B byte with a placeholder ([Trail of Bits](https://blog.trailofbits.com/2025/04/29/deceiving-users-with-ansi-terminal-codes-in-mcp/)). My recommended strip set adds bidi controls, zero-width and variation-selector ranges; no source quantified their exploitation against MCP agents, so that part is precaution. marq's attack surface is exactly these channels, since nmap, nuclei and curl relay banners, headers, DNS TXT and page titles verbatim, and `runner.Run` is the single choke point.

Benchmarks of the tool-description vector, MCPTox (o1-mini 72.8% ASR, refusals under 3%) ([arXiv 2508.14925](https://arxiv.org/html/2508.14925v1)) and MCP-SafetyBench ([arXiv 2512.15163](https://arxiv.org/html/2512.15163)), show how vulnerable agents are, but they concern server-supplied descriptions, which in marq are static and trusted, not third-party output.

## Architecture limits blast radius; marq can only enable it

CaMeL separates control and data flow so untrusted data cannot alter program flow and solved 77% of AgentDojo tasks with provable security versus 84% undefended ([arXiv 2503.18813](https://arxiv.org/abs/2503.18813)); Microsoft's FIDES reports stopping all AgentDojo injections with deterministic policy checks ([MSR](https://www.microsoft.com/en-us/research/publication/securing-ai-agents-with-information-flow-control/), secondary summary). Both are client-side designs, impractical for a user driving Claude Code or a llama.cpp agent. Meta's Rule of Two says a session should combine at most two of untrusted input, sensitive data and state-changing or external actions ([Meta](https://ai.meta.com/blog/practical-ai-agent-security/)). marq's OSINT reads are the untrusted-input leg, so the practical guidance is that a session ingesting OTX or WHOIS text should not also hold credentials and egress tools without human approval. Server-side, marq already scope-gates and audit-logs Active tools; it can additionally return typed output with an `outputSchema` and mark remote-controlled free-text fields, which fits the MCP spec's terse MUST to "Sanitize tool outputs" and client SHOULD to validate results ([MCP tools spec](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)). The MCP security best-practices page has no prompt-injection-via-output section ([MCP security](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices)). OWASP LLM01 asks for segregating and identifying external content, deterministic output validation, least privilege and human approval ([OWASP](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)); NCSC says injection will remain a residual risk and that deterministic controls outside the model matter most ([NCSC](https://www.ncsc.gov.uk/blog-post/prompt-injection-is-not-sql-injection)).

## Ranked recommendation for marq

| Rank | Action | Decision |
|---|---|---|
| 1 | Sanitize in `runner.Run` and in-process tool handlers: strip ESC/CSI/OSC, C0/C1 controls except newline and tab, U+E0000-E007F, zero-width, bidi, BOM, variation selectors; replace each with a visible `[U+XXXX]` marker; cap free-text length | Build in-house |
| 2 | Wrap third-party free text in a per-call random-nonce `<untrusted-output id=...>` block, neutralizing any occurrence of the delimiter in the payload; add one SKILL.md/system-prompt line that its content is data | Build in-house |
| 3 | Where tools have fixed schemas (whois, rdap, ct_search, ioc_lookup), return fields with `untrusted:true` on remote-controlled ones, and trim to fields needed | Build in-house |
| 4 | Document the Rule of Two for marq sessions; keep read and Active/egress tools separable | Document |
| 5 | Optional classifier: document a sidecar (Prompt Guard 2 22M or 86M, normalized input first, chunked) behind Docker MCP Gateway `after:exec`; user downloads weights, accepts the Llama license; marq ships nothing | Optional deployment |
| 6 | mcp-context-protector as a pinned-commit reference only, with an "archived" caveat | Document with caveat |

Not to adopt: bundling Prompt Guard 2 in the image (license pass-through, HF gating, 1 GB-class weights, cgo and tokenizer risk, and 7-70% indirect recall); ProtectAI v2 (archived, English-only, evasion-prone); Snyk Agent Scan, Lasso, Invariant Gateway defaults and Cloudflare (data leaves the host); ContextForge (heavy stack, advisory record); datamarking and encoding (breaks IOC fidelity, weak-model damage); any phrase deny-list (NCSC calls it fragile); and any marketing claim that marq "prevents" injection. Before adopting any classifier, measure false positives on real marq outputs including SPF and verification TXT records, since no published source covers that case.

## Conclusion

The evidence reverses the intuitive order of effort: the unglamorous layer (invisible-character stripping, provenance labelling, nonce framing, schema trimming) is cheap, deterministic, has no false positives on security tool output and closes channels that classifiers demonstrably miss, while the ML layer costs the most and delivers the least verified protection on exactly the indirect, tool-output case marq has. The honest framing for marq's docs is risk reduction plus blast-radius control, not prevention.

What remains uncertain is limited but material: no CPU latency for Prompt Guard 2, no pure-Go DeBERTa/mDeBERTa path confirmed, no measurement of any defense on benign instruction-like OSINT text, no study of nonce delimiters, and the full text of several 2026 papers was read only via summaries. A small local eval on marq's own outputs, as the 2026 detector-transfer study recommends, would resolve the classifier question before any engineering is committed.
